# Design decisions

One line per decision: what and why. Newest at the bottom.

- **2026-10-31 · .NET 10 (LTS).** The spec allows .NET 8+; .NET 10 is the current LTS and the installed SDK, and .NET 8 support ends Nov 2026.
- **2026-10-31 · PayPal client split into `IPayPalReadClient` / `IPayPalWriteClient`.** Agent tools only receive the read interface, so "the AI never moves money" is enforced by the compiler, plus a reflection test (`ArchitectureTests`).
- **2026-10-31 · Sandbox host allow-list in options validation.** `PayPal:BaseUrl` must be `https://api-m.sandbox.paypal.com` or the app refuses to start; a config mistake can't reach live PayPal.
- **2026-10-31 · Own retry loop instead of a resilience library.** Explicit and unit-testable; retries GETs and only POSTs that carry a `PayPal-Request-Id`, reusing the same key on every attempt; refreshes the OAuth token once on 401.
- **2026-10-31 · `PayPal-Request-Id` = `PendingAction.Id`, plus `custom_id` = action ID on refunds.** Retries are idempotent at PayPal, and each refund can be traced back to the approval that caused it.
- **2026-10-31 · Atomic claim on approval (`UPDATE … WHERE Status = 'Pending'`).** Double clicks and concurrent requests can't execute an action twice; the loser gets HTTP 409 (tested with 5 parallel approvals).
- **2026-10-31 · Re-validate against live PayPal state at approval time.** The capture may have been refunded (or the invoice paid) since the proposal; the same `RefundPolicy` runs at proposal and at approval.
- **2026-10-31 · Refund limits per currency (`Guardrails:MaxRefundAmount`).** A single USD 500 cap doesn't fit SGD/MYR; a currency with no configured limit can't be refunded at all (fail closed).
- **2026-10-31 · Refund history unknown ⇒ block.** If a capture is `PARTIALLY_REFUNDED` but its order can't be loaded, the remaining amount is unknown, so the refund is refused rather than guessed.
- **2026-10-31 · Pending proposals count against the refundable amount.** Stops "three USD 45 proposals on a USD 45 capture"; PayPal state is still the only truth at approval time.
- **2026-10-31 · Added `Summary` and `Payload` to `PendingAction` (beyond the spec model).** The card headline is built by code from verified PayPal data, not by the AI; `Payload` holds the exact reminder text the seller approves.
- **2026-10-31 · Prompt-injection text is withheld, not just flagged.** Customer-written fields that match injection patterns are replaced with a placeholder before the LLM sees them; the seller still sees the excerpt in the UI. Trade-off: some false positives hide harmless notes from the AI.
- **2026-10-31 · PII minimisation in tool results.** Emails are masked (`ai***@example.com`), addresses and payer IDs are dropped; the LLM never needs them for these tasks.
- **2026-10-31 · Strict validation of every LLM argument.** IDs must be plain letters/digits (blocks path tricks like `../oauth2/token`), amounts are parsed as `decimal`, strings are length-capped; invalid calls go back to the model as errors.
- **2026-10-31 · Official Anthropic C# SDK, beta endpoint.** Needed for server-side refusal fallbacks (`fallbacks: "default"`); no `temperature` (current Claude models reject sampling parameters), effort set explicitly (`medium`).
- **2026-10-31 · Default model `claude-opus-5-5`; Gemini via REST as the alternative.** One config switch (`Llm:Provider`); both sit behind `ILlmClient`, so the eval can compare providers.
- **2026-10-31 · Append-only conversation history; assistant turns replayed verbatim.** Claude thinking signatures and Gemini thought signatures must come back unchanged; a turn is committed only when it completes (refusals and truncated replies are dropped).
- **2026-10-31 · "Simple compaction" for long chats.** Past `Agent:MaxHistoryMessages`, history is replaced by a short text recap; trimming old turns would invalidate Claude's thinking blocks.
- **2026-10-31 · Static system prompt (no date or per-request values).** Keeps the prompt prefix byte-identical for prompt caching and thinking-block checks; tools return `as_of` dates instead.
- **2026-10-31 · Max 6 tool rounds and max 10 calls per round.** If the model still wants tools, the pending calls get "not run" results and the turn closes with a fixed message, so history stays valid.
- **2026-10-31 · In-memory conversations, SQLite for actions and audit.** Single demo seller; losing chat context on restart is acceptable, losing the audit trail is not.
- **2026-10-31 · Audit writes after a PayPal call ignore request cancellation.** If the client disconnects after a refund executed, the record must still be saved.
- **2026-10-31 · Shared `UserSecretsId` (`sellerpilot-dev`) plus optional `.env` loader.** One `dotnet user-secrets set` serves the API, the seed tool and the eval runner.
- **2026-10-31 · Seed tool tries card payments first, then buyer-approval links.** Card orders are fully scripted but need card processing in the sandbox app; the fallback needs one manual click per order and a `capture` step.
- **2026-10-31 · Eval runs in-process against the real LLM and sandbox, with a write client that refuses every call.** Deterministic checks (tools, proposals, amounts, reply text, flags), no LLM judge, so scores are reproducible and explainable.
- **2026-10-31 · Days overdue computed on the UTC date.** Can be off by one around midnight in Malaysia (UTC+8); good enough for the demo.
- **2026-11-01 · Token usage summed per message; tool results kept on each tool-call record.** Feeds the cost figures in the eval report and shows "what the AI saw" next to each step; Gemini prompt counts are stored without cached tokens so both providers mean the same thing.
- **2026-11-01 · The shop keeps its own books (customers, orders, ledger) next to PayPal.** Reconciliation needs two independent records; PayPal stays the source of truth for money, the ledger is what the shop believes happened.
- **2026-11-01 · Demo books built from seed-output.json with four planted mismatches.** Real sandbox IDs, deterministic problems (pending but shipped, overcharge, dashboard refund, payment without an order) so the demo and the eval can rely on them.
- **2026-11-01 · Reconciliation in code; refunds matched by PayPal ID, overcharge measured net of refunds.** Exact and explainable; a USD 12 correction refund clears an overcharge finding, a legitimate goods refund never creates one.
- **2026-11-01 · Executed refunds post to the books automatically; a PayPal ID can be booked once (unique index).** Posting runs after the action is saved as Executed, so a books failure never hides that money moved (it is audited and reconciliation catches it).
- **2026-11-01 · Books corrections are approval-gated actions that copy amounts from PayPal at approval time.** Changing financial records deserves the same propose/approve flow as moving money, even though nothing is paid.
- **2026-11-01 · Separate customer assistant: own prompt, tools, conversation store and owner check.** The seller's tools (refunds, reminders, search) are never reachable from the storefront; one customer can't continue another's chat.
- **2026-11-01 · Customer refund amounts come from code; the customer's click creates a request, the seller approves.** The assistant can't promise money; the button amount is the policy result, re-checked on submit.
- **2026-11-01 · Return-first above USD 100 / SGD 130 / MYR 450; return windows snapshotted on order lines.** Below the threshold, shipping a cheap item back costs more than it is worth; policy changes don't apply to past orders.
- **2026-11-01 · Cookie sign-in (HttpOnly, SameSite=Strict, JSON-only API) with seller and customer roles; demo password from configuration.** Closes the "approval endpoint has no auth" gap without an identity provider; sign-in is rate-limited (10/min per address).
- **2026-11-01 · The Eval tab starts the eval CLI as a process (Development only).** The UI and the terminal can never disagree; results are written atomically after each case for live progress.
- **2026-11-01 · Eval cost = token counts x list prices (cache reads ~10%, cache writes 1.25x input).** An estimate for budgeting; unknown models show no cost instead of a guess.
- **2026-11-01 · English-only demo names and original SVG product illustrations.** The demo should read the same for any audience, and drawn pictures avoid stock-photo licences; existing sandbox PayPal records keep their old item names until a re-seed.
- **2026-11-08 · Hosted demo on Render's free plan: one Docker container serves the API and the built React app.** Same origin keeps the SameSite=Strict cookie working; Vercel can't run the .NET API, and two hosts would mean two deploys for no gain.
- **2026-11-08 · `Shop:PublicDemo` (off by default) enables one-click sign-in without a password and a 10-messages-a-minute chat limit per address.** Judges and interviewers can try it without a password, and strangers can't run up the Claude bill; a local install keeps password sign-in.
- **2026-11-08 · Chat UIs label the assistant as AI.** Customers must know they are not talking to the shop owner.
- **2026-11-08 · Back office fits one screen; tabs and header actions look like buttons.** Only panel contents scroll, so the chat input and approvals stay in view; phones keep normal page scrolling.
- **2026-11-09 · The hosted public demo opens on a "Try SellerPilot" page with one-click buttons for the shop owner and each customer.** One link (for a resume or Devpost) reaches both the back office and the storefront; locally the root still shows password sign-in.
- **2026-11-09 · The eval and the demo video each get their own copy of the partly refunded order (seed `add` command).** A real refund uses an order up for good; an approved demo refund made 5 eval cases fail, so the eval now uses an order no demo should touch, and the shop adds new seed orders to an existing database on startup.
- **2026-11-09 · The eval runner refuses to start outside Development and says why (it protects the API credits).** On the hosted demo anyone could click Run; the UI now shows the server's reason instead of a generic "not allowed".
- **2026-11-12 · The hosted public demo approves in dry-run mode (`Shop:DryRunApprovals`): every PayPal check runs, the PayPal write is skipped (status NotSent).** A real refund uses an order up for good, so the first visitor would break the demo for everyone after; locally the setting is off and approvals really refund in the sandbox.
- **2026-11-12 · A freshly built shop books the refunds SellerPilot made earlier, recognised by the action ID in PayPal's `custom_id`.** The hosted demo starts with an empty database on every restart; without this, reconciliation would report its own past refunds as missing from the books. Refunds made elsewhere (no action ID) still show up as findings.
